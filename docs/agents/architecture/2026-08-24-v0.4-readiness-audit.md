# v0.4 Readiness Audit

Date: 2026-08-24

## Scope

This audit reviewed the published package boundary, scanner correctness, reporter metadata, monorepo detection, web scan hardening, dependency security, CI coverage, and the largest maintenance hotspots before v0.4 release preparation.

## Validated Baseline

- 315 package tests and 146 web tests pass (461 total).
- Build, workspace typecheck, and warning-free web lint pass.
- `pnpm audit --prod` reports no known vulnerabilities.
- Self-scan with `--preset app`: 100/100, excellent, 0 findings.
- Vulnerable fixture with `--preset strict`: 0/100, critical, 26 findings.
- Secure fixture with `--preset app`: 99/100, excellent, 1 LOW finding.
- SARIF output parses as version 2.1.0 and preserves 26 vulnerable-fixture results.
- All four publish packages pack with `dist`, `package.json`, `README.md`, and `LICENSE`; a clean local tarball install reports CLI version 0.3.0 and completes the secure-fixture scan.

## Correctness Fixes

1. Password analysis no longer treats an installed hashing dependency as proof that hashing is used.
2. Project detection recognizes nested `apps/*` Next.js routers without treating generic `src/api` folders as Next.js.
3. Nested `apps/*` and `packages/*` middleware signals carry an app scope and cannot suppress sibling-app findings.
4. SARIF rule metadata uses the strongest effective severity and confidence among findings sharing a rule ID.
5. GitHub metadata 403/429 responses are represented as upstream rate limits rather than private-repository errors.
6. Upstash concurrency rejection rolls back the request's rate-limit increment.
7. CLI version output and generated workflow pins read the package manifest instead of duplicated literals.

## Quality and Security Fixes

- The workspace requires Node.js 20.9+, while published packages declare Node.js 20+.
- The web demo and secure fixture use Next.js 16.3.2 with a clean production dependency audit.
- Root tests resolve workspace package source, preventing stale `dist` output from hiding regressions.
- Web typechecking is part of the root typecheck command.
- ESLint uses the supported CLI path and fails on warnings.
- CI now runs for pull requests, manual dispatches, and pushes to `main`.
- CI includes build, typecheck, warning-free lint, tests, and the security smoke check.

## Remaining Known Limitations

- The web scan timeout races the scanner promise but cannot cancel synchronous rule work already in progress. Cancellation would require an `AbortSignal` contract through core and rule execution and is deferred to a dedicated design task.
- TypeChecker analysis remains an opt-in experiment; default scans stay syntax-first.
- Cross-function and cross-file data flow remain intentional false negatives for v0.4.
- Test count is strong, but line/branch coverage thresholds are not yet enforced.

## Refactor Decision

Do not perform a big-bang rewrite before v0.4. The 1,300+ line `ast-utils.ts` module is the main maintenance hotspot, but behavior is now protected by regression tests and should be split incrementally after release correctness is stable.

Recommended sequence:

1. Extract shared parse/cache and `AnalysisFacts` types behind the current exports.
2. Move command-flow analysis into a dedicated module and rerun the 30-case bounded-flow matrix.
3. Move SQL, XSS, password, upload, and route intent analyzers one at a time.
4. Split `security-rules.ts` by category only after AST ownership is clear.
5. Add coverage reporting and thresholds after module boundaries stabilize.

Each extraction must preserve rule IDs, finding IDs, severities, evidence paths, output formats, SARIF fingerprints, fixture counts, and scan performance budgets.
