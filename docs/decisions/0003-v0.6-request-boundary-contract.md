# Decision 0003: v0.6 Request-Boundary Contract

Date: 2026-08-31

Status: Accepted for v0.6 planning and implementation

Issue: [#29](https://github.com/SetraTheXX/next-secure-check/issues/29)

## Decision

v0.6 extends the existing syntax-first, bounded-analysis model to request
boundaries that matter in current Next.js applications. It is a quality
release, not a pivot to full taint analysis.

The published v0.5.0 release tag is the frozen behavioral baseline. Every
v0.6 slice must document its source, sink or reviewed operation, guard,
evidence, context, and stop conditions before implementation. No v0.6 rule
behavior is authorized by this contract alone; each slice still needs its own
fixtures, focused tests, and release-gate evidence.

## Frozen v0.5 baseline

The baseline source is the validated v0.5.0 release tag at commit
051c3d8db65722b266ff864906a5e863fa4abe7c. The post-release main branch may
contain documentation-only changes, but it does not redefine this behavioral
baseline.

| examples/secure-next-app | app | 99/100 | excellent | 1 LOW |

The published validation baseline is 366 package tests, 147 web tests, and
513 total tests. The vulnerable-fixture SARIF baseline is SARIF 2.1.0 with
26 results, 19 unique rule IDs, and deterministic partial fingerprints.

Finding identity remains:

~~~text
${ruleId}:${filePath}:${line ?? 0}:${column ?? 0}
~~~

scannedAt and durationMs are volatile metadata and are excluded from
byte-for-byte determinism comparisons. Fixture counts are regression alarms,
not universal accuracy claims.

## Compatibility contract

All v0.6 slices must:

- preserve existing rule IDs, CLI flags, report formats, SARIF locations, and
  deterministic fingerprints unless a separate compatibility decision is
  accepted;
- keep detailed terminal output as the default and --summary as an opt-in
  terminal-only presentation;
- keep new metadata additive and explainable, without exposing raw secrets,
  tokens, sensitive URL values, absolute local paths, or stack traces;
- preserve the existing exit-code and --fail-on behavior;
- keep findings ordered deterministically by relative path, location, and rule
  identity;
- treat every result as a review signal, not proof of exploitability.

The existing 20 built-in rule identities are protected. New v0.6 behavior may
add a separately reviewed rule only when its identity and compatibility impact
are documented first.

Issue #31 follows this exception through [Decision 0004](./0004-v0.6-server-action-guard-signal.md):
it adds one new development-line identity while preserving the historical v0.5
20-rule baseline and all existing identities.

development-line identity while preserving the historical v0.5 20-rule

## Shared vocabulary

| Term | Contract meaning |
| --- | --- |
| Request boundary | A statically recognizable server/request entry point. It does not prove runtime reachability. |
| Source | A recognized request-derived value such as params, search params, request fields, form data, or action input. |
| Sink | A recognized security-sensitive operation that consumes the value. |
| Guard | A rule-specific visible check such as an auth check, schema validation, internal-path check, or host allowlist. It is never a universal safe flag. |
| Evidence | A short path or explanation emitted only when the syntax proves the bounded relationship. |
| Context | File and route context used to tune review priority; it does not prove execution or reachability. |
| Stop condition | A boundary where tracking must end instead of guessing. |

The boundaries above are review contracts, not promises that every matching
syntax is exploitable. Unknown wrappers remain unknown. A visible guard may
lower or suppress a signal only when the relevant slice explicitly recognizes
that guard.

## Shared analysis limits

The default path remains syntax-first and local. Unless a later decision
explicitly expands the scope, v0.6 does not add:

- cross-file or cross-function propagation;
- full CFG, call graphs, heap/property aliasing, or dynamic name resolution;
- default TypeChecker or project-graph analysis;
- a full middleware/auth route graph;
- unrestricted JavaScript/TypeScript plugin execution;
- network access, dependency installation, or execution of scanned repository
  code.

For source-to-sink slices, direct expressions, direct assignments, and the
existing short local alias boundary may be used. Reassignment, mutation,
closure/callback escape, function boundaries, dynamic properties, unknown
wrappers, and unsupported alias depth stop evidence propagation.

## Determinism, performance, and privacy budget

Each slice must run the existing pnpm release:gate checks and record the same
100-file and 1,000-file synthetic corpus measurements. The validation record
must include cold and warm scanner time, cold and warm process time, median,
p95, and analysis-overhead ratio on the same host and Node baseline.

An unexplained increase of more than 25% in scanner median or p95 against the
recorded v0.5 gate is a review blocker for that slice. An intentional increase
requires a validation note explaining the tradeoff and acceptance decision.
Privacy checks must continue to reject raw secret/token evidence, sensitive URL
values, absolute local paths, and scanned-repository execution.

2. issues #30–#35 link their boundary to this contract;

5. the existing build, typecheck, lint, test, and release-gate checks pass.
