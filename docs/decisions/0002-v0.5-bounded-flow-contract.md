# Decision 0002: v0.5 Baseline and Bounded-Flow Contract

Date: 2026-08-29

Status: Accepted for the v0.5 implementation line

## Decision

Before changing rule behavior, v0.5 uses the scanner implementation at commit
`ca2ad1dda1473074466dba0f08535358bc280625` as its behavioral baseline. The
baseline is recorded by fixture summary, finding identity, severity,
confidence, context, and report-format expectations.

The first v0.5 flow work remains deliberately bounded:

- syntax-first AST inspection remains the default path;
- propagation is local to one function and one source file;
- direct expressions, direct assignments, and at most two identifier-alias
  hops are supported;
- a source-to-sink path is reported as evidence only when the syntax proves
  that path;
- an unproven path may still produce the existing sink review signal, but it
  must not be presented as proof of exploitability.

This decision preserves the v0.4 public contract while giving #14 and #15 a
precise boundary to implement and measure.

## Finding identity contract

Finding IDs are deterministic and are preserved across v0.5 changes unless a
deliberate compatibility decision says otherwise:

```txt
`${ruleId}:${filePath}:${line ?? 0}:${column ?? 0}`
```

The relative `filePath`, rule ID, location, severity, confidence, and context
are the stable identity fields used in this baseline. `scannedAt` and
`durationMs` are run metadata and are intentionally excluded from byte-for-byte
baseline comparisons.

The complete baseline identity inventory is in the companion validation note:
[`phase-10-v0.5-baseline.md`](../validation/phase-10-v0.5-baseline.md). It
contains no raw source evidence, secret values, tokens, or local absolute
paths.

## Report contract

The existing public report formats remain compatible:

| Format | Baseline contract |
| --- | --- |
| Detailed terminal | Human-readable project metadata, score/risk, severity sections, rule ID, location, confidence, context, `Why`, context reason, and optional bounded evidence path/evidence/recommendation blocks. |
| Concise terminal `--summary` | Opt-in terminal-only view with score/risk, counts, and up to three deterministically ordered representative findings. It omits evidence and fix paragraphs and does not change scan findings. |
| JSON | Valid JSON containing project metadata, summary, findings, and scan metadata. Optional `evidencePath` is present only when a bounded path is proven. |
| Markdown | Stable heading/summary/finding sections carrying the same finding identity, `Why`, context reason, and optional bounded evidence path. |
| GitHub | Step-summary-friendly headings, compact findings table, and recommendation details carrying explanation metadata and optional bounded evidence paths without changing finding identity. Raw evidence remains omitted. |
| SARIF | SARIF `2.1.0`, one tool run, rule/result metadata, locations when available, context properties, optional `whyReported`/`evidencePath`, and deterministic `partialFingerprints`. |

The `--summary` view is already implemented in the local development line;
JSON, Markdown, GitHub, and SARIF behavior is unchanged by that presentation
option. No new format or plugin execution model is introduced by this
contract.

## AnalysisFacts vocabulary

`AnalysisFacts` is a shared syntax-fact boundary, not a universal taint or
safety verdict. Rule-specific facts must remain distinguishable.

| Fact | Meaning | Required boundary |
| --- | --- | --- |
| `source` | A recognized input origin such as `request.json()`, `request.formData()`, `req.body`, `req.query`, `searchParams.get(...)`, or route parameters. | Record a syntax-derived source label; do not claim reachability or exploitability. |
| `sink` | A recognized security-sensitive call or operation. | Keep sink detection working even when no source path can be proven. |
| `guard` | A rule-specific visible guard, such as an explicit same-function command allowlist. | Do not turn it into a universal `safe` or `sanitized` flag. |
| `alias` | A local identifier assignment that preserves a tracked value. | Follow direct assignments and no more than two identifier-alias hops. |
| `reassignment` | A later write, mutation, or assignment that invalidates a tracked value. | Stop the path at the invalidation; do not silently reuse stale source facts. |
| `function boundary` | A value entering or leaving another function, closure, or callback. | Do not propagate through the boundary in the bounded model. |
| `evidencePath` | A short human-readable source-to-sink chain. | Emit it only for a proven bounded path, for example `request.json() -> command -> alias`. Never place raw secret material in it. |
| `sourceFile` and cache identity | The AST/source object to which the facts belong. | Parse a source file once per scan lifecycle and keep facts read-only for consumers. |

The current implementation already has command-specific facts and a parse
cache. #14 may generalize the vocabulary only where it removes duplicated AST
work; it must not erase rule-specific meaning.

## Supported boundary examples

The executable 30-case matrix in
[`regression-fixtures.test.ts`](../../packages/rules/src/regression-fixtures.test.ts)
is the authoritative syntax-level coverage for the existing command-flow
pilot. The examples below describe the contract in reviewer-facing terms.

| Boundary | Unsafe/source example | Safe or no-source example | Expected interpretation |
| --- | --- | --- | --- |
| Direct source expression | `exec(request.json())` | `spawn('git', ['status'])` | The first has a source path; the second has no request-derived source. |
| Direct member/assignment | `const body = await request.json(); exec(body.command)` | `const command = 'git'; spawn(command, ['status'])` | Track the direct assignment only when its value is source-derived; static input does not create a tainted path. |
| Request/query/search/route sources | `exec(request.body.command)`, `exec(searchParams.get('command'))`, or `exec(params.command)` | A static executable and static argument array | Recognized input origins are bounded source labels; static command arguments do not become source evidence. |
| One- and two-hop aliases | `command -> alias -> second -> exec(second)` | An alias chain whose initial value is static | Follow at most two identifier hops; an untrusted path is not inferred from an unrelated static value. |
| Same-function local scope | A request-derived value used by a sink in the same function | An explicit same-function allowlist guard such as `['git', 'ls'].includes(command)` with early rejection | The guard can suppress the command sink when the syntax proves it; unknown wrappers remain review signals. |
| JS/JSX/TS/TSX and App/Pages Router syntax | The matrix's JS, JSX, TS, TSX, App Router, and Pages Router request-to-sink cases | The matrix's unrelated `object.exec()` and static non-shell spawn cases | File language and route style do not widen the data-flow boundary. |

“Safe” here means safe with respect to the bounded source path. A literal
`exec('ls')` can still retain the existing imported command-sink review signal;
absence of `evidencePath` is not a claim that a sink is safe.

## Intentional stop conditions

The bounded model stops evidence propagation at:

- reassignment or mutation of the tracked identifier;
- closure or callback escape;
- a function boundary or unknown wrapper;
- dynamic property/index resolution that cannot be represented as a direct
  member path;
- cross-file flow or module-level value resolution;
- alias chains beyond the two-hop limit.

These stops are intentional under-approximation. The scanner may retain a
review finding for a recognized sink, but it must not fabricate a source path
or label the result as proof of exploitation. The current matrix explicitly
covers reassignment, mutation, callback escape, and cross-function cases;
future foundation tests may make the remaining stop conditions more explicit.

## Non-goals for v0.5

This contract does not authorize:

- a full taint engine, call graph, or control-flow graph;
- heap or property aliasing beyond direct syntax-visible members;
- dynamic module/name resolution;
- cross-file or cross-function propagation;
- default TypeChecker or project-graph analysis;
- unrestricted JavaScript/TypeScript plugin execution;
- execution, installation, or import-time running of scanned repository code.

The last boundary applies to the CLI, web flow, tests, fixtures, and all
validation commands: the scanned repository is treated as input data only.

## Performance protocol

The protocol is fixed now; the release gate and repeated statistics belong to
#19.

| Field | #13 baseline record |
| --- | --- |
| Node / package manager | Node `v24.6.0`, pnpm `10.20.0` |
| OS / CPU | Windows 10 x64, AMD Ryzen 5 5600 6-Core Processor |
| Repository size | 167 tracked files, 92 JavaScript/TypeScript source files, 17 example files |
| Existing syntax gate | 100-file synthetic corpus; the Phase 6 note records directional `cold: 124.9ms`, `warm: 115.2ms` measurements |
| Cold run | Fresh process and fresh scan/cache state; record scanner wall time separately from fixture creation and process startup |
| Warm run | Repeat the same corpus in the same process after the first scan; record cache-hit behavior separately |
| Median / p95 | Not claimed by #13; #19 will use repeated cold and warm samples and publish median and p95 |
| Syntax-to-flow ratio | Not applicable before the next flow slice; #19 will compare the bounded-flow path with the syntax-only baseline on the same corpus |

The corpus, options, Node version, OS, CPU, file count, cold/warm state, and
sampling method must accompany future numbers. External repositories remain
optional smoke inputs and are not required CI dependencies.

## Change and review policy

If a future change alters a fixture result, reviewers must compare the
before/after rule IDs, severity, confidence, context, location, evidence path,
score/risk, and all report formats. The change must be classified as an
intentional improvement, an accepted limitation, or a regression requiring
repair. Exact fixture counts are regression alarms, not immutable promises.

No rule ID, CLI flag, report format, SARIF location, or deterministic
fingerprint may change incidentally while implementing #14 or #15.
