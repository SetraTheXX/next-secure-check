# Decision 0004: v0.6 Server Action Guard Signal

Date: 2026-08-31

Status: Accepted for the bounded #31 implementation

## Decision

Add one new rule, `auth/server-action-without-guards`, to the v0.6 development
line. Keep the existing v0.5 rule identities and behavior unchanged. The new
rule reports a deterministic review signal when a recognized Server Action or
Server Function consumes action/request input without visible authentication or
input-validation intent in that same function.

The rule uses one combined identity instead of separate auth and validation
rules. A function with neither recognized control produces a MEDIUM finding. A
function with exactly one recognized control produces a LOW finding that names
the missing control. A function with both controls produces no finding.

## Recognized boundary

- A top-level `use server` directive marks directly exported function
  declarations and exported function variables in the file.
- An inline `use server` directive at the start of a function body marks that
  function, including a nested Server Function whose reachability is not
  inferred through a call graph.
- A function with a direct parameter is treated as accepting action input.
  Static request-like values such as `request.json()`, `formData.get()`,
  `params.id`, `searchParams.get()`, `headers()`, and `cookies()` are also
  recognized when they are visible in the function.

## Recognized controls

The rule reuses the syntax-level v0.5 auth and validation intent vocabulary:

- known auth calls and role/permission checks from the route intent analyzer;
- validation calls such as `safeParse`, `parse`, `validate`, `isValid`, and
  `typeof` checks;
- static input allowlists, equality checks, and direct normalizer guards;
- short local input aliases, with reassigned aliases excluded.

Unknown local wrappers, framework adapters, data-access-layer checks, runtime
reachability, cross-file flow, dynamic exports, and type-aware taint remain
outside the boundary.

## Compatibility impact

The existing 20 built-in rule IDs, CLI flags, output formats, and SARIF
fingerprint formula remain unchanged. The development branch exposes one new
rule, so its built-in rule count is 21. The published v0.5.0 package and its
20-rule release-gate baseline remain historical and unchanged until a future
v0.6 release is deliberately published.

## Rationale

Next.js documents Server Actions and Server Functions as server-side entry
points that still require authorization and validation of client-controlled
input. A bounded, same-function signal gives ordinary Next.js developers an
actionable review location without claiming exploitability or building a full
taint engine.
