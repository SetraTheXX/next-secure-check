# Decision 0005: v0.6 Unvalidated Redirect Signal

Date: 2026-08-31

Status: Accepted for the bounded #32 implementation

Issue: [#32](https://github.com/SetraTheXX/next-secure-check/issues/32)

## Decision

Add one new rule, `redirect/unvalidated-target`, to the v0.6 development
line. Keep the published v0.5.0 package and its frozen 20-rule behavior
unchanged. The new rule reports a deterministic review signal when a
request-derived value reaches a recognized redirect sink without a visible,
rule-recognized destination guard.

The signal is not an open-redirect proof. It gives a short source path and
distinguishes dynamic/external-looking destinations from internal-relative
paths so the developer can review the redirect decision in context.

## Recognized sources

The bounded source vocabulary includes:

- `params`, `routeParams`, `searchParams`, `query`, and their static properties
  or `.get()` values;
- request-like values such as `request.url`, `request.nextUrl`, `request.body`,
  `request.json()`, `request.formData()`, and `req`/`context` equivalents;
- `formData.get()`, `headers.get()`, and `cookies.get()` when the container is
  visibly derived from a recognized request source;
- direct request-like function parameters and short local assignments within
  the same function.

Source paths are syntactic evidence only. The analyzer does not prove runtime
reachability, request provenance, or exploitability.

## Recognized sinks

The first slice recognizes only:

- named `redirect` and `permanentRedirect` imports from `next/navigation`;
- named `NextResponse` imports from `next/server` when used as
  `NextResponse.redirect(...)`;
- `getServerSideProps` return objects with a `redirect.destination` value.

`res.redirect`, `router.push`, `window.location`, `getStaticProps`, and
`next.config` redirect entries are intentionally outside this slice until a
separate contract exists.

## Recognized guards and severity

The signal is suppressed only for visible forms that this slice can recognize:

- equality against a static destination;
- a static array or `Set` allowlist checked with `includes` or `has`;
- an internal-path check that accepts `/` and rejects protocol-relative `//`;
- a same-origin comparison or a host/origin allowlist around the destination.
- a same-file helper whose single return expression visibly proves one of the
  internal-path or static-allowlist checks above.

Normalization or `new URL(...)` alone is not treated as proof. A dynamic or
external-looking destination remains MEDIUM. A destination with a visibly
internal-relative static prefix is lowered to LOW, because it still deserves
review for path handling and protocol-relative edge cases.

Unknown `isSafeRedirect`-style helpers do not count as recognized guards. If an
unknown call, reassignment, or mutation breaks the bounded source relationship,
the analyzer stops emitting evidence rather than guessing.

## Analysis boundary

Tracking is limited to the same function and the existing short local alias
budget of at most two hops. It stops at cross-file/cross-function flow,
closures/callback escape, dynamic properties, reassignment or mutation,
unknown wrappers, unsupported imports, client components, and dynamic sink
resolution. No scanned repository code is executed, no network request is
made, and no TypeChecker or full taint engine is introduced.

Evidence remains additive, deterministic, and privacy-safe: raw URL values,
tokens, secrets, absolute local paths, and stack traces are not emitted.

## Compatibility impact

The existing 20 built-in rule IDs, CLI flags, report formats, SARIF identity,
and v0.5 fixture baseline remain unchanged. The development line now exposes
two separately documented v0.6 rules (`auth/server-action-without-guards`
and `redirect/unvalidated-target`), bringing the development surface to 22
rules. The published v0.5.0 npm package remains a 20-rule release until a
future v0.6 release is deliberately published.
